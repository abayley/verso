MicroHttp — A Request's Journey

micro-http · branch main · 2026-06-13

A tour of the server, organised module by module as we follow one HTTP request from main down to the bytes on the wire. Read the chapters in order; each is a module, and each goes one layer deeper into handling the request.

This reflects the target design after RFC-0012 (the Application becomes a stream consumer and logging becomes middleware). The engine and transport chapters (Iteratee, Socket, Stream) show today's code, which RFC-0012 keeps; the Main, Server, and Middleware chapters show the RFC-0012 shape, which differs from the current source.
module seam — an Either error boundary the iteratee engine middleware layer

The shape of it

main hands Server.serve a Settings and one Application — a stack of middleware wrapped around a router. serve opens the listening socket and forks a capped handler per connection. Each handler drives the application stack with bytes read from the socket, through the iteratee engine, and writes the response back out. The request flows down the middleware stack to the router at the bottom; the response flows back up through the same layers — which is how the outermost layer, logging, sees both.

01

Main — wiring and serve

src/TestApp.hs · src/MicroHttp/TestApp.hs

The executable is thin: it picks the settings and the access-log destination and calls serve. The application itself — the middleware stack wrapped around the router — is composed in the MicroHttp.TestApp module's appWith, outermost-first: logging wraps the slow-client policy, which wraps the error-response mapping, which wraps the router. That one expression is the layering — no hidden pipeline. Logging is just the outermost middleware (RFC-0012 removed the old settingsLogger); the executable only injects which logger to use. 

src/TestApp.hs — design (RFC-0012)

main :: IO ()

    let settings = defaultSettings
    result <- Server.serve settings
                  (TestApp.appWith (fileLogfmtLogger "build/access.log"))
    ...

02

Server — the glue that ties it together

src/MicroHttp/Server.hs

Server owns the connection lifecycle and nothing HTTP-specific. serve opens the listening socket, sizes a counting semaphore to settingsMaxActiveHandlers, and loops accepting. Each accept yields the client socket and the peer address (decoded from the sockaddr accept already fills — no extra syscall). A handler is forked per connection, takes a semaphore slot, runs, and releases it — so in-flight handlers are bounded. 

src/MicroHttp/Server.hs — design (RFC-0012)

acceptLoop settings app sem socket = do
    accepted <- accept socket                -- (ClientSocket, ConnectionInfo)
    case accepted of
        Right (client, conn) -> do
            _ <- forkIO (runCappedHandler settings app sem client conn)
            acceptLoop settings app sem socket
        ...

-- the connection layer: drive the stack, write, close. No framing,
-- no parsing, no logging here -- those moved into the stack.
handleClient settings app client conn = do
    final   <- socketEnumerator client (readBuffer settings)
                   (idleRead settings) (app conn)   -- app :: ConnectionInfo -> Iter
    outcome <- run final
    _ <- case outcome of
        Right response -> writeResponse (socketSink settings client) response
        Left _         -> pure (Right ())   -- aborted: nothing to write
    closeClientSocket client

That is the whole of how Server ties it together: it produces bytes from the socket (socketEnumerator), feeds them into the application stack (app conn), drives it to a result with run, writes any response, and closes. Settings carries host, port, the handler cap, the byte limits, and the idle read/write timeouts — pure configuration, no logger.

03

Socket — bytes, readiness, and the peer

src/MicroHttp/Network/Socket.hs

Every socket is non-blocking. recv returns whatever is in the kernel buffer right now — one byte up to the read buffer (8 KiB) — and only parks when the buffer is empty. It never waits to fill the buffer, so the first chunk is the first packet's worth, delivered immediately. A would-block read parks on the runtime poll queue via waitForReadFD (RFC-0005 readiness), bounded by an idle deadline (RFC-0006); writes mirror it with sendAllWithin (RFC-0008). Every operation returns Either SocketError — the dashed seam. 

src/MicroHttp/Network/Socket.hs

-- one recv per chunk; returns available bytes, parks (bounded) if empty
recvWithin :: Int -> ClientSocket -> Int -> IO (Either SocketError ByteString)

-- accept now decodes the peer from the sockaddr it already fills (RFC-0012)
accept :: ListenSocket -> IO (Either SocketError (ClientSocket, ConnectionInfo))

data ConnectionInfo = ConnectionInfo { connPeerHost :: Host, connPeerPort :: Port }
04

Iteratee — the engine

src/MicroHttp/Iteratee.hs

An iteratee (Iter e a) is a stream consumer paused in one of four states; an enumerator is a producer that feeds it. They play a turn-based game: the consumer says NeedInput, the producer hands it a chunk, it steps forward, until Done or IterFailed. The core is HTTP-free — the failure type e is a parameter — and effects live only in IterM, so the pure NeedInput continuation can hand leftover bytes (residue) straight on without a read. 

src/MicroHttp/Iteratee.hs

data Stream e = Chunk ByteString | EndOfStream (Maybe e)

data Iter e a = Done a (Stream e)            -- result + residue
              | NeedInput (Stream e -> Iter e a)  -- pure continuation
              | IterM (IO (Iter e a))          -- an effect step
              | IterFailed e (Stream e)        -- terminal failure + residue

type Enumerator e a = Iter e a -> IO (Iter e a)
run :: Iter e a -> IO (Either e a)

A request in three chunks

The chunk size is whatever recv returns (up to settingsReadBufferBytes, 8 KiB; file response bodies stream in fileChunkBytes, 4 KiB — the two are independent constants). Suppose a slow network delivers POST /save … Content-Length: 11 … hello world in three reads. Here is how the constructors and residue thread through:

recvbytes deliveredframe / parse / bodyiteratee state
1 "POST /save HTTP/1.1\r\nContent-Len" logger taps first line → logs RQST (peer, POST, /save); framing buffers, no \r\n\r\n NeedInput (wants more)
2 "gth: 11\r\n\r\nhel" framing finds \r\n\r\n → Done head; residue "hel" is the body start, threaded by bind into parse → takeN 11 (app head) Done head, then body consumer NeedInput (has 3 of 11)
3 "lo world" takeN feeds the last 8 bytes (11 total), then EndOfStream to the handler; handler builds the Response Done Response

Note how nothing waits for an 8 KiB buffer: each recv delivers what arrived, framing accumulates across chunks, and the body bytes that arrived with the header terminator are not re-read — they ride along as residue.

05

Stream — sockets and files as producers

src/MicroHttp/Stream.hs

socketEnumerator is the producer that drives the application: on each NeedInput it does one recvWithin and feeds the chunk; an empty read is an orderly EndOfStream, a read error or idle timeout ends the stream carrying a StreamError (a timeout becomes StreamTimeout). This layer fixes the engine's generic e to the server's StreamError vocabulary. The mirror producer, fileEnumerator, streams a file in 4 KiB chunks and owns the handle (released on every exit) — it is how a static-file response body is produced. 

src/MicroHttp/Stream.hs

socketEnumerator socket bufferSize idleMicros = loop
  where
    loop it = case it of
        NeedInput k -> do
            received <- recvWithin idleMicros socket bufferSize
            case received of
                Left err -> return (k (EndOfStream (Just (toStreamError err))))
                Right bytes
                    | BS.null bytes -> return (k (EndOfStream Nothing))
                    | otherwise    -> loop (k (Chunk bytes))
        IterM m -> m >>= loop
        _ -> return it
06

Middleware — the bidirectional stack

src/MicroHttp/Middleware.hs

An Application takes the connection metadata and consumes the raw request stream; a Middleware wraps one. Because the application now sits in the byte stream, a middleware can tap the request as it flows down and observe the response as it flows back up — the two directions the access log needs. 

src/MicroHttp/Middleware.hs — design (RFC-0012)

type Application = ConnectionInfo -> Iter StreamError Response
type Middleware  = Application -> Application

logRequests        :: Logger -> Middleware   -- outermost: first line, peer, sizes, time
withErrorResponses :: Middleware             -- StreamParseError -> 400, StreamTimeout -> 408
flowchart TD subgraph stack [Application stack] direction TB LG["logRequests"] --> SC["slow-client policy"] SC --> ER["withErrorResponses"] ER --> RT["routing (bottom)"] end REQ["request bytes ▼"] --> LG RT --> RSP["Response ▲"] RSP -. "flows back up" .-> LG

logRequests is outermost. It has the peer from ConnectionInfo immediately, taps the first line off the stream to log RQST, tallies request bytes as it forwards them, and — when the response flows back up — reads the status and counts the response bytes (via egress), logging RESP with sizes and round-trip time. A connection that dies mid-headers still gets a terminal ABRT.

The slow-client guard splits. The hard deadline for a silent socket stays at recvWithin (a stalled thread is parked below the stack, where no middleware runs). A slow-client middleware above it enforces rate/deadline policy when chunks arrive, and logging — being outermost — records the outcome for every client.

07

TestApp — routing at the bottom

src/MicroHttp/Router.hs · Static.hs · TestApp.hs

Routing is the innermost layer and the one that actually frames and parses. serveRoutes is the bottom Application: it frames the head, parses it, bounds the body to the declared Content-Length, and dispatches to a Handler — which still receives a parsed RequestHead (now carrying requestPeer, filled from the connection). This answers "why was framing so far up?": it no longer is — it is the bottom of the application stack, not a server pipeline. 

src/MicroHttp/Router.hs · Static.hs — design (RFC-0012)

serveRoutes :: ParseLimits -> [Route] -> Application
serveRoutes limits routes _conn =
    frameAndParse limits >>= \head ->
        takeN (declaredBodyLength head) (route routes head)

type Handler = Captures -> RequestHead -> Iter StreamError Response
data PathPart = Lit String | Capture String | Rest String   -- * wildcard = static

A handler reads the bounded body (e.g. readBodyStrict for a form post) and returns a Response whose body is a StrictBody (in memory) or a StreamBody (a file via fileEnumerator, used by Static.serveStatic).

08

Writing back — and completion

src/MicroHttp/Http/Response.hs · Server.hs

The Response flows back up the stack (logging reads its status). The server writes it: a StrictBody goes out as one serialised buffer with Content-Length; a StreamBody writes a close-delimited head then drives its enumerator into the sink. The bytes pass through the logging middleware's egress tap, so it counts the response and stamps the last-byte time. Each write is bounded by the idle write timeout (sendAllWithin, RFC-0008). Then the logger emits the terminal line and the socket closes. 

build/access.log — logfmt

event=RQST peer=127.0.0.1 method=POST path=/save
event=RESP peer=127.0.0.1 method=POST path=/save status=200 bytes=42 dur_ms=3

The connection then closes — MicroHttp sends Connection: close per response. Keep-alive is deliberately a non-goal: a reverse proxy owns client keep-alive, and its default upstream mode is one connection per request, matching this. The per-request Application would compose under a future keep-alive loop without changing shape.
