Architecture review — the Haskell tree

packages/micro-http/src (19 modules, ~5,300 lines) and packages/verso/src/Verso (26 modules, ~8,100 lines; App.hs is 2,290 of them and the hottest file since July) · 2026-09-16 · main @ 4c061f6

module seam leakage deep module
The streaming core is deep: one bracket, one failure shape, every byte path a row in one table. The friction is above it. The structural operations of the document tree (move, delete, restore, undo) have no module: the filesystem half is in TreeMove, the transaction half (operation log, link index, draft, revision) is in the request handlers, and every one of them is reachable from a test only by building raw HTTP bytes. Most candidates below are that observation, cashed out. Test note: the coverage run is GHC, which swaps in a different UTF-8 codec and file-open shim (test/ghc-compat), so the production codec is exercised only by the mhs suites.

After — one interface, one transaction

Verso.Structure (or Reorganisation)

move :: Target -> Destination -> Confirm -> IO (Either Refusal MoveOutcome)

delete, restore, undo :: ... -> IO (Either Refusal Outcome)

filesystem
(TreeMove)
operation log
link index
draft
revision (git)
write lock

Handlers shrink to: parse request → call → render outcome. Outcomes are data; JSON is rendered once, in the handler.

Problem. The ordering contract "apply, append to the operation log, maintain the index, relocate the draft, commit a revision" lives in four handlers and the undo core, each rebuilding the log record by hand (App.hs:526, 563, 600, 756, 764); nothing tests that ordering except 1,155 lines of integration requests.

Solution. Move the transaction into one module whose interface is the four structural operations returning outcome values; TreeMove becomes its filesystem implementation, and the log record is built in one place.

  • locality: the transaction ordering has one home
  • leverage: undo reuses move/restore, not a copy
  • tests hit one interface, no Request bytes
  • delete: five hand-built log records, three draft helpers in App
  • preview and apply share a type, not just a code path
ADR-0060/0064 fix what a move does and that the log is append-only; this changes only where the steps are joined. No conflict.

Root, tree-relative page path, section path and trash id are all String; moveSection :: RelevantPages -> FilePath -> String -> String -> String -> Bool (TreeMove.hs:117) is told apart by argument order.

After — one place knows the layout

Verso.TreePath

parent, slug, metaDirectory, peerAssets, trashEntry

The mass moves inward: ~40 resolution sites become calls; the sandbox check and the meta-dir convention become one implementation each, tested as pure functions.

Problem. The document tree's layout (where a page, its meta directory, its peer assets and its trash entry live) is knowledge spread across five modules as string arithmetic, so a layout change or a path-safety fix has ~40 edit points and one unsandboxed variant.

Solution. A path module with newtypes for the three path kinds and the trash id, one resolver, one parent/slug/meta/assets derivation; callers hold typed paths, not strings.

  • locality: layout and sandboxing fixed once
  • interface: argument order stops carrying meaning
  • delete: three parent-dir impls, two segment splitters
  • pure, tested without a filesystem
  • prerequisite that shrinks candidate 1
Touches the open MicroHs file-name limit (docs/reviews/microhs-filepath-encoding-bug-report.md): a typed path is also the one place a UTF-8 route through our own FFI would be decided. Do not decide it here; leave the seam.

4 · The framework joins body types to body producers, not the application

Worth exploring in-process

MicroHttp/Http.hs:145-154, 437-451 · MicroHttp/Stream.hs:257-279 · MicroHttp/Middleware.hs:63-71 · MicroHttp/Server.hs:222-236 · Verso/App.hs:2087-2160

Before — four parties know the body taxonomy

Http defines StrictBody | StreamBody | SizedStreamBody | FileBody; writeResponse dispatches
Stream builds the producers (transformedFileBody, transformedTempFileBody) but no Response
Middleware.fuseBody re-matches all four, no-ops two
Verso.App is the only constructor of StreamBody/SizedStreamBody; runs the Content-Length counting pass under onException with no test (App.hs:2131)
Server.socketSinkFile re-stats the file and distrusts the size FileBody carries (Server.hs:230)

After — body construction is an interface of the framework

MicroHttp.Http (or Stream)

streamedFileResponse :: Status -> Headers -> Framing -> Prefix -> BlockTransform -> FilePath -> Suffix -> IO (Either NotFound Response)

data Framing = Chunked | Sized -- the counting pass lives here

mapBody :: (Enumerator -> Enumerator) -> Response -> Response

App keeps only the document-specific prefix/suffix and the escaper. The counting pass and its missing-file path get a framework test with fault injection.

Problem. Serving a streamed document is a framework capability whose only implementation is in the application, so the framework has no test of its own Content-Length pre-count and the taxonomy is matched in three modules.

Solution. Export a response constructor from the framework that takes the transform and framing choice and owns the count; keep the four constructors but make mapBody the one place that walks them.

  • leverage: Verso gains three fewer response helpers
  • locality: taxonomy matched once (mapBody)
  • the untested onMissing path gets a unit test
  • decide FileBody's size: trusted or dropped
Brushes ADR-0034 ("sendfile with the size carried"): the writer already ignores that size (Server.hs:222-234). Worth reopening only to record which of the two the type means.

After

Iteratee

foldChunksI :: (s -> Bytes -> m (Either e s)) -> s -> IterT e m s

cappedI :: Int -> e -> IterT e m a -> IterT e m a

fileSinkI = cappedI limit err (foldChunksI write h); foldBlocksI, foldLinesI (via linesI) and readBodyStrict are instances. One percent-decoder on bytes; Http's String twin decodes through it.

Problem. Stream and Iteratee are split by error type rather than concept, so Stream hand-writes consumers the core could express, and two modules implement the same RFC 3986 rule.

Solution. Two general consumers in the core (an effectful fold, a cap) that the file sink and the folds instantiate; one byte percent-decoder.

  • locality: the consumer loop has one implementation
  • leverage: the cap becomes reusable (Form's tooLarge, uploads)
  • delete: one hexPair, ~40 lines of loops
  • keep the MicroHs slice rule; test with the existing StreamSpec
Each combinator is a dictionary and an allocation per chunk under MicroHs (streaming-algebra.md, "not missing"); bench make bench-iteratee before and after.

Problem. The maintenance seam is real (two adapters: link index and search) but typed as five untyped closures; Git's failures are partly values and partly silence, so "not a repo" and "no history" are the same answer.

Solution. A maintenance event type with one handler function; Git returns a result from every call. Only worth it once candidate 1 gives these a single caller.

  • a recording adapter tests ordering without an index
  • Git silence becomes data (correctness, not depth)
  • the search worker still needs its own unit seam; not designed here

Noted, not candidates

  • Frontmatter imports SearchChunks for isDashesLine alone (Frontmatter.hs:29): move one function.
  • Static.safeComponent is cited by FileSystem's header as the validator callers must use, but is private (Static.hs:74).
  • Router.notFound and Static.notFoundResponse are the same response in two modules.
  • Access log decodes the request target byte-per-Char (Middleware.hs:236) while Http.pathSegments decodes UTF-8: the two conventions disagree on a non-ASCII path.
  • Four framework modules have no Haddock module header: Html, Router, Server, Network.Socket.
  • Server.reportConnectionFailure writes to stderr outside the Logger (Server.hs:143), by its own admission.
  • Runtime gaps already recorded on the architecture page (an IO mapChunksI, runNested3, a pull cursor) stay deferred; nothing found here needs them.

Top recommendation

2 · The tree layout as a module, then 1 · structural operations

Candidate 2 is pure, mechanical, and passes the deletion test at ~40 sites; it is the smallest change that makes candidate 1 tractable, because a structural-operations interface written over untyped strings would inherit every ambiguity TreeMove has now. Candidate 1 is where the leverage is: it is the only way the move/delete/undo transaction gets a test that is not an HTTP request, and it takes roughly 600 lines out of the route module.
