# RFC-0044 and RFC-0045 code review: tree paths and structural operations

Status: review (2026-09-16). Change set: `4c061f6..e2fe316` on `main`, six commits. 15 source and
test files, about 1,800 insertions and 1,270 deletions: the new `Verso.TreePath` and
`Verso.Structure`, `Verso.TreeMove` rewritten over typed paths, `Verso.DocumentMeta` and
`Verso.Draft` retargeted, `Verso.App` reduced from 2,290 to 1,867 lines, `MicroHttp.Static`
exporting `safeComponent`, two new specs, and the glossary, architecture page and RFC records.

The review ran along the two usual independent axes, each in its own sub-agent: Spec (does the
code do what RFC-0044 and RFC-0045 say, and are the documents accurate) and Standards (does the
code follow the documented conventions and avoid the Fowler smell baseline). A third sub-agent
desk-traced and probed the correctness questions the change raises: path containment, trash ids,
behaviour parity of the move and delete refusals, and the ordering and lock coverage of the
structural transaction. Its findings are kept in their own section. The sections are not
reranked against each other. Each finding is labelled MEASURED (a command or probe was run),
VERIFIED (the code was traced end to end) or INFERRED (a plausible reading not confirmed by
execution).

Baseline for the review, all MEASURED at `e2fe316`: `make check` passes in full (mhs unit 605,
mhs integration 150, the same under GHC, the editor checks, both smokes and the chrome gates).

## RFC-0044/0045 Correctness Findings

Ranked by severity. One finding is a real defect in the undo and replay paths; the rest are
recorded behaviour changes or parity notes.

### Correctness 1: undo and replay mis-target a section whose name ends in `.md`

MEASURED (GHC probe), VERIFIED in both callers.

`TreePath.slug` derives the kind from the last segment
([TreePath.hs:90](../../packages/verso/src/Verso/TreePath.hs#L90)), so the slug of `dest/foo.md`
is `foo` even when the operation log says the path names a section. Both places that previously
honoured the recorded kind now use it: the move inverse in
[Structure.hs:333](../../packages/verso/src/Verso/Structure.hs#L333) (the old code used
`slugForPath (opKind op) from`) and replay in
[TreeMove.hs:647](../../packages/verso/src/Verso/TreeMove.hs#L647) (the old `slugOfPath kind to`).

Scenario: `moveSection` accepts a raw slug `foo.md` (`safeComponent` allows it), producing the
section `dest/foo.md` and a record `kind: section, to: dest/foo.md`. Undo now moves it back to
`foo` rather than `foo.md`; replay lands it at `dest/foo`, so a later record for `dest/foo.md` is
skipped. The forward handler cannot itself operate on such a section (kind-by-suffix picks
`movePage`), which is pre-existing.

Fix: select the slug by the record's kind in both places (`if isPage then TreePath.slug else
TreePath.name`), and refuse a section slug ending in `.md` in `moveSection` so the state cannot
arise.

### Correctness 2: the trash batch operations lost lock coverage

VERIFIED against `git show 4c061f6:packages/verso/src/Verso/App.hs`.

The old empty-trash handler and retention sweep held the write lock across the catalogue read
and every removal. Now `treeTrashEmptyHandler`
([App.hs:586](../../packages/verso/src/Verso/App.hs#L586)) reads the ids outside any lock and
`Structure.purge` locks per entry; `purgeExpiredTrash`
([App.hs:551](../../packages/verso/src/Verso/App.hs#L551)) and the listing handler take no lock
around the read. Each purge is atomic and a purge of a just-restored entry returns `False`, so
the only effect is a stale row or count in that one response. Recorded in RFC-0045's Reliability
Impact. Wrapping the two loops in `Structure.withWriteLock` restores the old coverage cheaply.

### Correctness 3: undoing a restore answers with the referrers JSON

VERIFIED. `deleteInto` returns `StillReferenced` and the undo path propagates it
([Structure.hs:349](../../packages/verso/src/Verso/Structure.hs#L349)), so the reply is the
referrers object where the old handler sent the text "cannot undo restore: the target is now
referenced". The undo page ignores the body (`packages/verso-editor/src/undo-page.ts:59`), so
nothing breaks; a wire change to record.

### Correctness 4: undo now carries drafts

VERIFIED. Undo reuses `restoreEntry` and `deleteInto` with only the commit silenced, so undoing a
delete brings back a stashed draft and undoing a restore stashes one. The old inverse did
neither. This is an improvement in behaviour, but RFC-0045 says "no behaviour change observable
over HTTP", the `undo` Haddock still says draft consistency is not maintained, and the
refactoring log records it as deferred. Decide: keep and record, or silence the draft moves in
the inverse as the commit is silenced.

### Correctness 5: minor message and ordering changes

VERIFIED. The move handler collapses "unsafe source path" and "unsafe destination path" into
"unsafe path" (recorded). A move slug containing `/` was accepted and split into nested segments;
`TreePath.child` refuses it (recorded, a tightening). Create checks the path and the kind before
the title, so a request wrong in two ways reports the path first (recorded). The undo refusal
"delete record has no trash id" became "has no valid trash id". `restoreItem` leaves an item whose
manifest origin does not parse and then removes the manifest; manifests are self-written, so this
is unreachable in practice.

### Correctness 6: the questions that checked out clean

- Path containment (MEASURED): every constructor goes through `safeComponent`; the derived paths
  add fixed safe segments or drop one; backslash, NUL, `.` and `..` are refused; `//a/b/`
  canonicalises exactly as the old segment split did; `resolve "" p` yields `/a/b`, as the old
  `buildPath` did.
- Trash ids (VERIFIED): every trash path in `TreeMove`, `Structure` and `App` is built from a
  parsed `TrashId`; `trashIdForSeq` is `Nothing` only for a log holding a negative `seq`;
  `listTrash` skipping non-digit names drops only hand-made directories and closes the old
  unchecked `restoreFromTrash` id.
- Move parity (VERIFIED): the refusal set and order match; `within` on segments equals the old
  string-prefix cycle check; the empty-slug defaults match.
- Transaction ordering (VERIFIED): move, delete and restore are effect-for-effect identical to
  the old handlers and run under the lock; the silenced commit yields exactly one commit per
  undo. Apply-then-append with no rollback on an append exception is pre-existing.
- Draft relocation (VERIFIED): the parent-directory creation equals the old for root-level and
  nested pages, and section drafts still move as directories.

## RFC-0044/0045 Spec Findings

### Spec 1: a ticked RFC-0044 item is incomplete

VERIFIED. RFC-0044 phase 4 says `lastSegment`, `splitOn` and the duplicate trimmers are
"replaced or deleted" and is ticked. `lastSegment` survives at
[App.hs:946](../../packages/verso/src/Verso/App.hs#L946) (the refactoring log records it as
deferred, correctly), and `trimSpace` now exists in both `App` (no callers, dead) and
`Structure`.

### Spec 2: undo reuses two of the three operations

VERIFIED. RFC-0045's goal "undo reuses move, restore and delete" is met for restore and delete
through `restoreEntry` and `deleteInto`, but the move inverse calls `TreeMove` directly and
re-implements the applied branch ([Structure.hs:327](../../packages/verso/src/Verso/Structure.hs#L327))
minus the draft relocation. The fix for Correctness 4 decides which way this goes.

### Spec 3: unrecorded behaviour changes

VERIFIED. Undo carrying drafts (Correctness 4) is not in RFC-0045's Reliability Impact and
contradicts its "no behaviour change" line. The navigation tree now hides a directory entry whose
name is not a safe segment ([App.hs:1050](../../packages/verso/src/Verso/App.hs#L1050)); the
old listing showed it. The undo refusal wording change (Correctness 5). Delete, restore and purge
statuses are otherwise unchanged, and ADR-0091's bounded-read sites moved intact.

### Spec 4: the "append then commit" sentence

INFERRED. RFC-0045 says the spec asserts "append then commit"; delete and restore commit before
appending, as they always did. The code preserves behaviour; the RFC sentence is wrong for those
two operations.

### Spec 5: document inaccuracies

VERIFIED. The RFC-0044 proposal table omits the exported `Kind (..)`, `append`, `within` and
`trashIdForSeq`. RFC-0045 says `App` is 1,868 lines; it is 1,867. `CONTEXT.md` tells writers to
avoid "trash id" while the type is `TrashId`, the field `deletedTrashId` and the wire key
`trashId`. A mechanical rename left the comment "Structure.Versioning on: autosave stages a
draft" at [App.hs:1255](../../packages/verso/src/Verso/App.hs#L1255). The RFC index and the
architecture page match the code.

## RFC-0044/0045 Standards Findings

No hard violations were found: every `src` binding has Haddock, imports are qualified, no lazy
IO, no MicroHs-only syntax, refusals are values, and the new I/O spec is in the integration tier.
The items below are judgement calls against the smell baseline, plus one pre-existing item the
change touched.

### Standards 1: the page-or-section dispatch is written three times

VERIFIED. `if isPage then TreeMove.movePage else TreeMove.moveSection` appears at
[Structure.hs:233](../../packages/verso/src/Verso/Structure.hs#L233),
[Structure.hs:332](../../packages/verso/src/Verso/Structure.hs#L332) and
[TreeMove.hs:645](../../packages/verso/src/Verso/TreeMove.hs#L645). One `TreeMove.moveNode`
dispatching on the kind would remove all three, and is the natural place for the Correctness 1
fix.

### Standards 2: the kind still travels as a string

VERIFIED. `TreePath.Kind` exists, but `deletedKind`, `restoredKind`, `TreeMove.delKind`,
`OperationLog.opKind` comparisons and `Trash.manKind` comparisons carry `"page"`/`"section"`, and
there are two `kindWord` functions with different domains (`App.hs:364`, `Structure.hs:397`) plus
`kindString` at `App.hs:1029`. `TreeMove.Deleted` renders a `TrashId` to a string that
`Structure.deleteInto` ignores in favour of the typed one it already holds. The log's wire words
are the boundary; inside it one `Kind` and one wire-word function would do.

### Standards 3: rendered-then-reparsed paths

VERIFIED. `breadcrumbsFor` and `treeSpineFor` render a validated path to a string so the
exported, string-tested `linkedFolderPaths` can re-parse it
([App.hs:933](../../packages/verso/src/Verso/App.hs#L933)). A `TreePath -> [TreePath]` core with
a string wrapper for the test would drop the round trip.

### Standards 4: inconsistent parse edge and a flag by record update

VERIFIED. `Structure.purge` takes a raw string and parses, while `restore` takes a `TrashId` and
the handler parses; pick one side. `applyInverse` silences the commit with
`structure{structureCommit = \_ _ -> pure ()}`; a boolean parameter on `deleteInto` and
`restoreEntry` would be more legible.

### Standards 5: duplication in tests and small helpers

VERIFIED. The parse-or-error fixture helper is copied five times across the new and updated
specs; one `test/support` helper would do. `trimSpace` and `trim` now exist in eight modules
(moved, not added). `Structure.commitRevision` writes to stderr directly, moved unchanged from
`App`; the record already injects the commit, so a log sink could ride along.

### Standards 6: pre-existing items touched

INFERRED. `DraftSpec`, `DocumentMetaSpec` and `TreeMoveSpec` do filesystem I/O under `build/`
and live in `test/unit`, against STANDARDS.md; the change re-plumbed them without moving them.
`App`'s re-exports use the qualified form `Structure.slugify`, where ADR-0069 describes an
unqualified import kept for the re-export list; the qualified form is valid and clearer.

## Summary

Correctness: six sections, one defect (the undo and replay slug for a section named like a page),
one lost lock coverage, two recorded-or-unrecorded behaviour changes. Spec: five findings, the
worst being the undo draft change that RFC-0045 says did not happen. Standards: no hard
violations; the worst judgement call is the three-way page-or-section dispatch, which is also
where the correctness fix belongs.

## Remediation Summary

Applied on 2026-09-16, after the decisions to keep the undo draft behaviour and to restore the
whole-sweep lock. Every change was made test-first and every gate below was rerun.

### Remediation of the correctness findings

- Correctness 1 (fixed, tested): `TreeMove.moveTarget` and `TreeMove.slugOf` dispatch on an
  explicit `TreePath.Kind`; the undo inverse and replay take that kind from the operation log
  record, so a section named like a page moves back to its recorded path. Two new tests: a redo
  through `Structure.undo` and a replay through `TreeMove.replayLog`, both with a section slug
  ending in `.md`. This also removes the three-way page-or-section dispatch (Standards 1).
- Correctness 2 (fixed, tested): `Structure.purgeMatching` runs the catalogue read and every
  removal under one hold of the write lock; the retention sweep and emptying the trash call it.
  A new test purges by predicate and checks the kept entries.
- Correctness 3 and 5 (recorded): the referrers JSON on a refused undo of a restore, the
  refusal wording, and the create check order are in RFC-0045's Reliability Impact.
- Correctness 4 (kept, recorded): undo carries drafts. The `undo` Haddock, RFC-0045 and the
  refactoring log now say so.

### Remediation of the spec findings

- Spec 1: the dead `trimSpace` in `App` is deleted; the RFC-0044 phase 4 item now records that
  `lastSegment` stays over a parse for the search title callback.
- Spec 2: the move inverse now goes through `moveTarget`, sharing the dispatch and the slug rule
  with the forward move; the draft relocation on a reversed move remains a difference, recorded.
- Spec 3 and 4: the behaviour changes and the commit-before-append order for delete and restore
  are in RFC-0045's Reliability Impact.
- Spec 5: the RFC-0044 table lists `Kind`, `append`, `within` and `trashIdForSeq`; the line
  count reads "about 1,860"; the glossary's "Trash entry id" no longer tells writers to avoid the
  code's own name; the stray qualified comment is fixed.

### Standards findings left as they are

Standards 2 (the kind as a string in the outcome records and the log comparisons), 3 (the
rendered-then-reparsed breadcrumb paths), 4 (`purge` parsing its own id; the silenced commit), 5
(the fixture helper and the trimmers) and 6 (I/O specs in the unit tier) are judgement calls
recorded here for a follow-on; none affects behaviour.

### Verification after remediation

MEASURED: `make format`, `make lint`, the mhs unit suite (606 examples) and integration suite
(152), the same under GHC, and the full `make check`.
