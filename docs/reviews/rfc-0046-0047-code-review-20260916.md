# RFC-0046 and RFC-0047 code review: JSON value type and trash mechanics

Status: review (2026-09-16). Change set: `30f4a71..34382cc` on `main`, five commits. About 420
insertions and 300 deletions across 13 source and test files: the new `Verso.Json` and its spec, the
API renderers rebuilt on it, the four `View` JSON primitives and `TreeMove`'s `jsonStr` plus two dead
renderers deleted (RFC-0046); the trash filesystem mechanics moved from `Verso.TreeMove` into
`Verso.Trash`, a new `Verso.Trash` seam test, and the `TrashStore -> TreeMove` dependency removed
(RFC-0047); and the glossary, architecture page and RFC records.

The review ran along the two usual independent axes, each in its own sub-agent: Spec (does the code do
what RFC-0046 and RFC-0047 say, and are the documents accurate) and Standards (documented conventions
and the Fowler smell baseline). A third sub-agent desk-traced and probed correctness: byte-for-byte
parity of every converted JSON renderer, the escaper, and the byte-identity of the moved trash
functions. The sections are not reranked against each other. Each finding is labelled MEASURED (a
command or GHC probe was run), VERIFIED (traced end to end) or INFERRED.

Baseline for the review, all MEASURED at `34382cc`: `make check` passes in full (mhs unit 610, mhs
integration 158, the same under GHC, the editor checks, both smokes, the chrome gates).

## RFC-0046/0047 Correctness Findings

No correctness defects. The one intended behaviour change, control-character escaping, is a strict
improvement and reaches no real payload.

### Correctness 1: JSON output is byte-identical except for the declared escaping fix

MEASURED (GHC probe on `Verso.Json.render`), VERIFIED across the converted renderers.

Every converted renderer (`createdJson`, `deletedJson`, `restoredJson`, `undoneJson`, `referrersJson`,
`trashEntriesJson`, `treeChildrenJson`, `searchResultsJson`, `TreeMove.movePlanJson`,
`View.attachmentsJson`, `View.breadcrumbsJson`, `treeSpineFor`) is a mechanical swap to `Json.*` with
the same field order. `render` preserves field order, emits `{}`/`[]` for empties, keeps nesting, and
renders an integer unquoted through `show`. The old raw-number splices (`show pending`,
`show (length purged)`) become `Json.int`, which renders identically and stays unquoted
([Json.hs:61](../../packages/verso/src/Verso/Json.hs#L61)); the unit `AppSpec` still asserts
`"pending":2`. The escaper adds the short forms `\b` and `\f` and `\u00XX` for the rest of U+0000 to
U+001F ([Json.hs:77-89](../../packages/verso/src/Verso/Json.hs#L77)); DEL and non-ASCII are emitted
verbatim as before and UTF-8-encoded downstream. The only difference from the old five-character
escaper is that a control character, previously emitted raw as invalid JSON, is now escaped.

### Correctness 2: the moved trash functions are byte-identical

MEASURED (diff against `git show 30f4a71:.../TreeMove.hs`), VERIFIED at the call sites.

`moveIntoTrash`, `moveDirIntoTrash`, `restoreItem`, `targetOccupied`, `listTrash`, `deleteTrashEntry`
and `removeTree` in [Trash.hs:149-224](../../packages/verso/src/Verso/Trash.hs#L149) are byte-identical
to the old `TreeMove` bodies once the now-redundant `Trash.` qualifier is normalised. The callers
(`applyPageDelete`, `applySectionDelete`, `restoreFromTrash`, `TrashStore.loadTrashEntries`,
`Structure.purgeEntry`) pass the same arguments in the same order. `Verso.Trash` imports only
`Verso.TreePath` (which imports no `Verso` module) and `MicroHttp.FileSystem`, so no cycle.

### Correctness 3: the test-fixture path collision is resolved and no other exists

VERIFIED. The integration `Verso.TrashSpec` uses `build/trash-mechanics-spec`
([TrashSpec.hs:12](../../test/integration/Verso/TrashSpec.hs#L12)) and the unit `Verso.TrashSpec` uses
`build/trash-spec`; no two specs in either suite share a `build/` root. The two same-named modules live
in separate suite binaries. The integration spec cleans at the start of each case, the codebase's
pattern.

## RFC-0046/0047 Spec Findings

### Spec 1: an RFC-0046 test item is claimed but not delivered

VERIFIED. RFC-0046's Testing section promises "a property that `render` never emits a raw byte below
U+0020 inside a string". `test/unit/Verso/JsonSpec.hs` is entirely example-based: it checks U+0000,
U+0001 and U+001F individually, not the invariant across the range. nanospec has no property-testing
support, but the RFC lists the item as delivered. Either add a hand-rolled check over the whole control
range or correct the RFC. This is the only real gap in either change.

### Spec 2: everything else is faithful

VERIFIED. No wire-shape change beyond the escaping fix. The RFC-0046 non-goal holds:
`OperationLog.renderOperation` is untouched and the `/operations` endpoint splices it through
`rawJsonResponse` ([App.hs:463](../../packages/verso/src/Verso/App.hs#L463)). The RFC-0047 non-goals
hold: the warm catalogue and the retention sweep are not merged into `Verso.Trash`, and the manifest
format, on-disk layout and the tree parts of delete and restore are unchanged. The RFC-0047 goal holds:
`TrashStore` imports only `Verso.Trash` now. Both RFCs' proposal tables match the exported signatures.
The glossary, architecture page and RFC index are accurate.

## RFC-0046/0047 Standards Findings

No hard violations. `Verso.Json` has a module header and per-function Haddock; imports are qualified;
`Verso.Trash`'s new imports are all used; the deletions left no dangling reference or unused import
(`Data.List` is gone from `View`, still used in `TreeMove`); the pure `JsonSpec` is in the unit tier
and the I/O `TrashSpec` in the integration tier.

### Standards 1: a dead statement and its import in the seam test

VERIFIED. The last integration `TrashSpec` case ends with `Monad.void (pure ())`
([TrashSpec.hs:99](../../test/integration/Verso/TrashSpec.hs#L99)), which asserts nothing and is the
only use of `Control.Monad` in the file. Drop the line and the import.

### Standards 2: the smart constructors alongside public constructors

Judgement call. `Verso.Json` exports both `Json (..)` and the helpers `object`/`array`/`string`/`int`/
`bool` that are plain aliases of the constructors. The helpers read better at call sites and the
constructors are needed for pattern matching in the spec, so both earn their place; noted as a
deliberate choice, not a change.

## Summary

Correctness: three sections, no defects, all parity claims MEASURED or VERIFIED. Spec: two findings,
the only real one being the escaping property test claimed as done but not written. Standards: no hard
violations; one dead statement to delete.

## Remediation Summary

Applied on 2026-09-16. Both findings were addressed; every gate below was rerun.

### Remediation of the spec finding

- Spec 1 (fixed): `test/unit/Verso/JsonSpec.hs` gains the invariant the RFC promised, as two cases: the
  render of a string holding every C0 control character (U+0000 to U+001F), and the render of control
  characters mixed with printable text, each asserting the output holds no raw byte below U+0020. This
  is an exhaustive example over the enumerable control range, since nanospec has no property testing;
  RFC-0046's Testing section is reworded to say so.

### Remediation of the standards finding

- Standards 1 (fixed): the dead `Monad.void (pure ())` and the now-unused `Control.Monad` import are
  removed from the integration `TrashSpec`.

### Standards left as they are

Standards 2 (the smart constructors exported alongside the public constructors) is a deliberate
choice, kept.

### Verification after remediation

MEASURED: `make format`, `make lint`, the mhs unit suite (612 examples) and integration suite (158),
the same under GHC.
