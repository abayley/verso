# RFC-0040 phase 1: request and response path baseline (2026-09-11)

Baseline measurements for RFC-0040, taken before any change, on the real corpus at the current default heap.
The headline is that two of the surveyed paths are worse than the survey's cost model predicted, and one of
them is not a memory multiplier at all but a functional limit that users can reach today.

## Baseline measurement setup

| Item       | Value                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------ |
| Binary     | `build/verso` (MicroHs), commit `7e610bf`                                                  |
| Heap       | `+RTS -H8000000 -RTS` (the current `VERSO_HEAP_CELLS` default, ~122MB arena)               |
| Config     | `build/cello-profile.conf`: real corpus, 3,980 documents, search off, port 8081            |
| Versioning | On, so saves stage a draft under `build/cello-profile/drafts` rather than writing the tree |
| Machine    | The developer's own desktop (Darwin arm64), otherwise idle                                 |
| RSS        | `ps -o rss=`, polled every 100ms for the duration of each request                          |

Startup on this corpus took 16.3s (cold link-index build) and settled at 140MB RSS, which is the 122MB arena
plus the runtime. That is the number every delta below is measured against.

## Document render baseline

The largest document in the real corpus is 263,076 bytes
(`cello-smartsecure/zscaler-management/zscaler-customer-info/zscaler-customer-summary-mitre10.md`).

| Request                 | Duration | Response bytes | RSS delta |
| ----------------------- | -------- | -------------- | --------- |
| `GET` read view         | 141ms    | 356,481        | ~6MB      |
| `GET ?edit` editor view | 100ms    | 356,662        | ~6MB      |

The render path is the healthiest of the three. It holds several copies of the document (read, escape, page,
concat) but at 263KB that is a few megabytes against a 122MB arena, and the wall time is dominated by useful
work. Item 3 in the RFC's inventory is real but is the lowest priority of the three request-path items, which
is a change from the survey's ordering.

## Form save baseline

`POST /documents/<path>` with an `application/x-www-form-urlencoded` body of `markdown=<content>`, content
being ASCII text with `%0A` newline escapes. Body size is the raw request body, which is what `formBodyLimit`
caps at 1 MiB. Each request went to a fresh scratch path.

| Body size | Duration         | Notes                                                                                                           |
| --------- | ---------------- | --------------------------------------------------------------------------------------------------------------- |
| 16KB      | 0.24s            | includes first-request warmup                                                                                   |
| 32KB      | 0.02s            | the reliable small-body figure                                                                                  |
| 64KB      | 30.08s           | 2x the body, ~1,200x the time                                                                                   |
| 128KB     | 160.72s          | 2x the body, 5.3x the time                                                                                      |
| 1,007KB   | did not complete | client gave up at 300s; the server was still at 100% CPU on the request afterwards, and never logged a response |

This is the finding that matters most. The save path is not merely a ~24x memory multiplier as the survey
estimated; between 32KB and 64KB it falls off a cliff and then grows faster than quadratically. RSS stayed
flat at ~137MB throughout, so this is spent CPU, not growth.

### Which save path this is, and which one the editor uses

The measurement above is of `treeSave`, the `POST /documents/<path>` form handler. **It is not the path the
editor uses**, and an earlier revision of this ref wrongly concluded from it that editing a large document
is broken. It is not.

The editor's `saveMarkdown` issues `PUT` with the Markdown as a raw body
(`packages/verso-editor/src/server-client.ts`), which lands on `draftPut` (`PUT /drafts/*path`) for autosave
and `treePutDocument` (`PUT /documents/*path`) for publish. Both take the body as bytes and write it
straight out; neither decodes a form or builds a `String` (the `BS.unpack` in `treePutDocument` feeds
`publishMessage`, which is lazy and reads only the frontmatter head). That is RFC-0036's raw-body write
path, and it measures as healthy at the same 8,000,000-cell heap:

| Body size | Raw `PUT /drafts` | Peak RSS | Form `POST /documents` |
| --------- | ----------------- | -------- | ---------------------- |
| 128KB     | 2.5ms             | +3MB     | 160.72s                |
| 263KB     | 2.2ms             | +5MB     | not reached            |
| 1,024KB   | 8.9ms             | +10MB    | did not finish         |

So the corrected consequences are:

- **Saving from the editor is fine at every size up to the cap**, including the largest corpus document, and
  a body at the full 1 MiB `formBodyLimit` takes 9ms. `readBodyStrict`'s `BS.concat` costs little here
  because a 1 MiB body arrives in ~256 chunks; it is the 10 MiB upload's ~2,560 chunks where the
  O(total x pieces) fold turns expensive.
- **The broken path is the no-JavaScript fallback.** `View.hs` renders a `name="markdown"` textarea as the
  progressive-enhancement fallback (RFC-0001), and that form posts to `treeSave`. A reader without
  JavaScript cannot save a document over roughly 64KB. That is a real defect with a real, narrow audience,
  not a break in the main editing flow.
- **The 1 MiB `formBodyLimit` is unreachable on the form path** while being comfortable on the raw path, so
  the same constant means two different things depending on which handler reads the body.

This reduces phase 2's urgency from "the product is broken" to "a fallback path is broken, and the RFC's
no-document-sized-`String` goal is not yet met". It does not change the phase ordering: phase 2 is still
small, still first, and it is the cheapest of the three fixes.

The cliff shape (flat, then sudden, then super-quadratic) does not look like the per-character cost of the
`String` passes, which would be linear with a large constant. Every pass in the chain is linear and lazy
(`BS.unpack`, `splitOn`, `break`, `Http.decode`, `normaliseNewlines`), and MicroHs's `BS.pack` grows its
buffer geometrically (`bsappbyte` in `eval.c` multiplies capacity by 1.5), so it is amortised linear too.
The likely cause is the fixed arena: once the `String` working set approaches the 8,000,000 cells, every
allocation triggers a mark-and-sweep over the whole arena, so time grows with the square of the live set.
If that is right, RFC-0039's tight heap converted this space bug into a time bug, which is why it has been
invisible: the server never crashes, it just stops finishing.

### Heap-control experiment for the save cliff

The hypothesis was tested the same day by re-running the ladder at `-H32000000` (a 488MB arena, four times
the default), one request at a time. It is confirmed, and the confirmation is more useful than expected.

| Body size | At 8,000,000 cells | At 32,000,000 cells                                    | Speedup |
| --------- | ------------------ | ------------------------------------------------------ | ------- |
| 64KB      | 30.08s             | 0.044s                                                 | ~685x   |
| 128KB     | 160.72s            | 0.085s                                                 | ~1,900x |
| 256KB     | not taken          | did not finish; still at 99% CPU after 150s, abandoned | --      |

Two things follow. First, **the save path is linear when the arena has headroom**: 2x the body costs 1.93x
the time (0.044s to 0.085s). Nothing in the chain is algorithmically quadratic, exactly as reading the code
suggested. The 8,000,000-cell figures were measuring garbage collection, not work.

Second, and this is the important half, **raising the heap does not fix the problem, it only moves the
cliff.** At 8M cells the cliff sits between 32KB and 64KB; at 32M cells it sits between 128KB and 256KB.
Four times the arena buys four times the body size, which is what a live set proportional to the body
predicts. Reaching the 263KB corpus document would take roughly 64M cells (~1GB), and the 1 MiB
`formBodyLimit` roughly 256M cells (~4GB), for one concurrent save.

So the fix is not heap sizing, it is removing the live set: the `String` round-trip costs on the order of a
hundred cells per body byte across the five simultaneous passes (`BS.unpack`, `splitOn`, `break`,
`Http.decode`, `normaliseNewlines`, then `BS.pack`), and the arena needs free space to collect in on top of
that. Phase 2's byte-level decoding removes essentially all of it, which should make the existing
8,000,000-cell default comfortable rather than requiring a bigger one. That keeps RFC-0039's tight,
fail-fast heap intact, and it is the reason this RFC's Non-Goals still rule out raising
`VERSO_HEAP_CELLS`.

The experiment also explains why the tight heap never reported `heap exhausted` on this path. The collector
always finds something to reclaim, because the passes are lazy and the intermediate cells die as they are
consumed; it simply has to run almost continuously to do it. The failure mode of a nearly-full arena here is
unbounded time, not a crash.

## Asset upload baseline

`POST /documents/<path>?asset` with a raw body at the 10 MiB cap (`treeAssetMaxBytes`), filename supplied in
`X-Attachment-Filename`.

| Measure      | Value                             |
| ------------ | --------------------------------- |
| Duration     | 5.57s                             |
| RSS baseline | ~137MB                            |
| RSS peak     | 698MB                             |
| Spike        | ~560MB for a 10MB body, about 56x |
| Stored bytes | 10,485,760, exactly as sent       |

The survey described this as "two copies of a ten-megabyte body". It is about fifty-six. The spike is
consistent with `readBodyStrict`'s `BS.concat` over roughly 2,560 socket chunks being `foldr append`: each
step allocates a new buffer holding everything so far, and all of them are live until the fold finishes.
Note also that this memory is `malloc`'d ByteString payload, outside the cell arena, so the upload path
inflates RSS without ever reporting `heap exhausted`. That is why the tight heap did not catch it either.

## Concurrency measurement not taken

The planned concurrency measurement was four simultaneous 10 MiB uploads. It was run once and it exhausted
the machine's RAM. The server process was observed above **25GB** of resident memory before the desktop
session restarted. Two of the four requests had reported 24.1s and 111.6s before the machine went down.

That 25GB is the most alarming number in this baseline, and it is not a linear extrapolation of the
single-request spike: four requests at the measured ~560MB each would be ~2.2GB, so the per-request cost
under concurrency is roughly 6GB, an order of magnitude worse. The likely reason is that a ByteString's
payload is `malloc`'d rather than allocated in the cell arena, so it does not count toward the pressure that
triggers a MicroHs collection. On a single request the arena filled from the `String` and list allocation
alongside the fold, a collection ran, and the finalizers freed the intermediate buffers as it went. With
four concurrent folds, the intermediates -- roughly 2,560 buffers per request, averaging half the body --
are garbage almost immediately but nothing prompts the collector to notice, so they accumulate until the OS
refuses.

If that is right it is a defect worth stating plainly: **the upload path's memory is invisible to the
collector's trigger heuristic, so under concurrency it grows without bound rather than being reclaimed.**
That is a denial-of-service lever, not a performance wrinkle, and it raises the priority of phase 3's
streaming sink relative to what the single-request figure suggested. It also means neither of RFC-0039's
safety nets applies: not the tight arena, which this memory bypasses, and not `heap exhausted`, which never
fires.

These numbers are an observation from an aborted run, not a repeatable measurement, and the run should not
be repeated as designed.

This was a mistake in test design, not a discovered limit, and it should not be repeated on a workstation.
When the concurrency figure is needed it should be taken with a hard bound: two concurrent requests rather
than four, a smaller body (1 MiB, scaled up arithmetically), an `ulimit -v` or a container memory cap on the
server process, and RSS sampled by the harness with an abort threshold. Better still, take it after phase 3
lands, when the expected answer is a bounded buffer per request and the test is no longer dangerous.

The security point in the RFC no longer rests on the single-request figure alone. A ~560MB transient per
at-the-cap upload would already let a handful of simultaneous uploads exhaust a modest host; the observed
25GB says four are enough to exhaust a developer workstation. What the bounded re-run is for is a defensible
per-request number and confirmation of the trigger-heuristic explanation, not to establish that the problem
exists.

## Corrections to the RFC-0040 inventory

Phase 1 exists to correct the survey where measurement disagrees with it. Three corrections:

| Inventory item                    | Survey said                          | Measurement says                                                        |
| --------------------------------- | ------------------------------------ | ----------------------------------------------------------------------- |
| `treeSave` `String` round-trip    | ~24x memory multiplier               | a functional limit: unusable past ~64KB, and corpus documents exceed it |
| `treeUpload` and `storeAsset`     | two copies of the body               | ~56x the body in transient RSS, outside the cell arena                  |
| Document render whole-page concat | 4-5 copies per response, ranked high | real but cheap at corpus sizes; lowest priority of the three            |

The phase ordering in the RFC (form decoding, then upload streaming, then response streaming) is confirmed
by these numbers, and phase 2's justification is stronger than the RFC currently states.

## Phase 2 outcome: byte-level form decoding, and a stack overflow that was not what it looked like

Phase 2 replaced the `String` round-trip with a byte-level decoder (`Http.decodeFormValueBytes`,
`Http.parseFormBody`) and byte-level newline normalisation. The first cut produced this ladder at the
8,000,000-cell default:

| Body size | Before (String) | After (bytes), first cut           | After (bytes), final |
| --------- | --------------- | ---------------------------------- | -------------------- |
| 64KB      | 30.08s          | 0.158s                             | 0.16s                |
| 128KB     | 160.72s         | 0.380s                             | 0.23s (256KB)        |
| 256KB     | not measured    | `ERR: stack overflow`, server dies | 0.23s                |
| 512KB     | not measured    | overflow                           | 0.42s                |
| 1,007KB   | did not finish  | overflow                           | 0.92s                |

The first cut was 400x faster and then killed the server, so the overflow had to be understood before
anything landed. What follows is what the investigation established, in the order the evidence came,
because several plausible explanations were wrong.

### Where the stack overflow was

- MicroHs's evaluator stack is a fixed **250,000 slots** (`STACK_SIZE` in the runtime's `eval.c`), not
  derived from the heap; `+RTS -K` sets it. Nothing in this project had ever set it.
- The runtime's `mark()` (the collector) **uses that same stack** as its mark stack, pushing one slot per
  unmarked application node it descends (`if (!is_marked_used(*to_push)) PUSH`). Already-marked
  arguments are not pushed, so shared constants and lazy `i+1` counters cost nothing.
- A diagnostic build (a backed-up patch to the installed `eval.c` making `stackerr()` print its state)
  showed the fatal collection began with the evaluation stack **44 deep**. The 249,954 pushes were all
  `mark()`'s, one per byte of the value, while marking the **main thread's root** (thread 1, blocked in
  `waitRdFd` on `accept`), which reaches the request handler's graph through the forked action. There is
  no missing tail call in the program.
- Standalone reproductions were timing-dependent -- the same binary passed or overflowed at the same
  size depending on where a collection landed -- which is why only the server, with its fixed startup
  heap, reproduced reliably. Forcing a collection at a known point did not reproduce it either, because
  the two shapes I forced it inside (a lazy list feeding `BS.pack`, a lazy index accumulator) are not the
  shape at fault.

### What was at fault

Bisection in the server, one substitution at a time, named it. Replacing `BSC.elemIndex` in
`parseFormBody` with a strict `BS.index` loop moved the crash from 256KB to 512KB; also replacing
`BS.notElem` in the newline normaliser removed it entirely, through the 1 MiB cap. Both calls were
introduced by phase 2 itself. In MicroHs they are the **same library path**:

- `Data.ByteString.elemIndex c = Data.List.elemIndex c . unpack`
- `Data.ByteString.elem c ps = case elemIndex c ps of ...`, and `notElem = not . elem`
- `Data.List.elemIndex x = findIndex (x ==)`, `findIndex p = ... findIndices p ...`

`unpack` is eager (the runtime builds the whole list in C), and `findIndices`' scan leaves one
unevaluated application per element live while it runs -- the diagnostic showed each pushed node as a
compiled predicate application `C' S' (== c) (P K ...)` with a fresh argument at every level. A
collection landing during a scan of more than ~250K bytes therefore overflows. The same holds for
`BS.findIndex`, `BS.any` and `BS.all`, which are `Data.List.f . unpack` too.

Ruled out along the way, each by measurement: the decoder's per-byte lazy list into `BS.pack` (constant
heap, ~25K slots at 256KB, never overflowed even at 1.2M cells); `BS.pack` retaining its history;
the body assembled through `readBodyStrict`; the iteratee machinery; the link-index size; per-thread
stacks (mhs has none); the raw `PUT` path (fine at 1.5M cells); and decoding in bounded blocks, which
did not move the threshold because the depth was never in the decode.

### What landed

`Http.byteIndex`, a strict index loop over O(1) views, used by `parseFormBody`; the same shape for the
carriage-return check in `normaliseNewlineBytes`. Nothing else changed. The full 1 MiB `formBodyLimit`
is now reachable on the form path at the default heap and default stack, and the regression test at the
cap runs in the unit suite.

Two things follow for the project. First, the memory note for mhs's ByteString cost model gains a
second trap: the unpack-based scans are not just O(n) per call, they can kill the process. Second, this
is worth raising upstream: a collector that marks on the evaluator's fixed stack turns heap pressure into
a crash, and a stack that does not scale with the heap makes the default a poor fit for a server.

### Audit of the other unpack-based scans

Every non-primitive `Data.ByteString` function in mhs is `Data.List.f . unpack` (checked in the library
source: `elemIndex`, `findIndex`, `elem`, `notElem`, `any`, `all`, `split`, `splitWith`, `lines`, `words`,
`break`, `span`, `takeWhile`, `dropWhile`, `filter`, `foldl`, `foldl'`, `foldr`, `isInfixOf`, `isPrefixOf`,
`isSuffixOf`, `count`, `map`, `reverse`). Only the primitives (`length`, `take`, `drop`, `splitAt`, `index`,
`append`, `pack`, `unpack`, `replicate`, equality) are safe. The two packages had sixteen call sites; four
take document- or corpus-sized input and moved to `MicroHttp.Bytes`, a framework module of strict index
loops over O(1) views (`indexOf`, `split`, `isInfixOf`, `foldl'`), each characterised against the library
function and exercised at 1.2MB from a packed-chunk fixture. The other twelve are bounded (a request head,
a stream chunk, a line) and are listed in the RFC inventory with their bounds.

None of the four could be provoked standalone, but neither could `elemIndex`, which crashed the server every
time; the decision rule is input size, not a standalone probe. The one measurable path is the index reload
at startup, which runs `parseRows` over the 1.2MB persisted index: 8.3s before, 7.1s after on the real
corpus at the 8,000,000-cell default (two runs each; the remainder is per-field `BS.unpack` and map
construction, which RFC-0029 accepts).

## Phase 3 outcome: the upload streams to disk

`Stream.fileSinkI` writes each chunk to a temp file reserved in the assets folder, checks the cap before
every write, and removes the partial file on the cap, on a transport failure and on a file that will not
open; `storeAsset` renames the complete file into place and de-duplicates with `Stream.filesEqual` (size by
`stat`, then 64KB blocks). `TreeMove.assetConflicts` uses the same comparison. The refusal paths drain the
body through a discard sink so, as before, nothing is left on the connection.

| Measure, 10 MiB upload, 8,000,000 cells | Before                | After                 |
| --------------------------------------- | --------------------- | --------------------- |
| Duration                                | 5.57s                 | 1.03s                 |
| Resident memory above baseline          | ~560MB                | ~11MB                 |
| Stored bytes                            | 10,485,760, identical | 10,485,760, identical |
| Temp files left                         | n/a                   | 0                     |

One request at a time on the real corpus, corpus restored afterwards. The bounded concurrency measurement
deferred from phase 1 is now safe in principle, with an expected cost of roughly 11MB per in-flight upload,
and is still to be taken with the bounds the phase-1 note requires. ADR-0088 records the decision.

### The bounded concurrency measurement, and the defect it exposed

Two concurrent 10 MiB uploads against the demo corpus at the 8,000,000-cell default, with a harness that
kills the server if resident memory passes 500MB, three runs:

| Run | Upload 1     | Upload 2     | Peak resident above baseline | Bytes identical | Temp files left |
| --- | ------------ | ------------ | ---------------------------- | --------------- | --------------- |
| 1   | 200 in 1.06s | 200 in 1.06s | 3MB                          | 2 of 2          | 0               |
| 2   | 200 in 1.06s | 200 in 1.07s | 3MB                          | 2 of 2          | 0               |
| 3   | 200 in 1.05s | 200 in 1.04s | 31MB                         | 2 of 2          | 0               |

Against phase 1's four uploads exhausting the host, the per-request cost is now a fixed buffer, as
ADR-0088 predicts. Two 100KB uploads behave the same way.

The first attempt at this measurement failed in a way that had nothing to do with memory: in every run
exactly one of the two uploads succeeded and the other left a 0-byte temp file, the server stayed alive,
nothing reached stderr, and the failing client saw its connection closed with no response. Bisection by
substitution found it: the temp file was reserved with `IO.openTempFile`, which in MicroHs probes each
candidate name by opening it for reading and closing it, then opens the winner read-write. Done from one
connection thread while another connection was streaming its body, that open-and-close stranded the other
connection; naming the path from the thread id with a `stat` probe and no open (`FileSystem.uniqueTempPath`)
made both uploads succeed in every run. Two green threads streaming 10MB each into files with `hPut` are
fine standalone, so it is the open-and-close, not file I/O under concurrency. `Process.runProcess`
reserved its capture files the same way from the same connection threads and now uses the new function.

Why it was invisible: `Server.runCappedHandler` ran `handleClient` with no exception handler, so whatever
escaped there killed the connection thread silently and leaked its semaphore slot. Fixed the next day:
`handleClient` catches an escaping exception, closes the socket and returns it as `ServerHandlerCrashed`,
which the connection loop reports to stderr like any other connection failure, and the slot is released
under `finally`.

## Phase 4 result: streamed document responses (2026-09-12)

Phase 4 streams a document page in constant memory behind an exact `Content-Length` (ADR-0089). Measured on
the real corpus at the 8,000,000-cell default (`MICROHTTP_CONFIG=build/cello-profile.conf build/verso +RTS
-H8000000 -RTS`, port 8081), largest document (263,076 bytes), one request at a time.

| Metric                          | Phase 1 baseline | Phase 4             |
| ------------------------------- | ---------------- | ------------------- |
| `GET` read view response bytes  | 356,481          | 356,394             |
| `GET ?edit` view response bytes | 356,662          | 356,575             |
| Warm read latency (median)      | 141ms            | ~32ms               |
| Resident memory                 | ~6MB above idle  | plateaus, no growth |

The response-byte differences from the phase-1 baseline (87 bytes on read, 87 on edit) are corpus drift: the
tree is a live-edited working copy and breadcrumb and title labels changed between the two dates. Against a
build of the pre-phase-4 `HEAD` on the *same* corpus at measurement time, the streamed read view (356,394
bytes) and edit view (356,575 bytes) are byte-identical, and the `Content-Length` header matches the received
body exactly in both.

Memory is now bounded by the shell plus one 64KB block plus one 16KB segment, not the document: resident
memory plateaus at ~151MB across 100 sequential reads of the largest document with no per-request growth (the
~140MB is the arena plus the warm link index, unchanged from the startup baseline). The transient window
between collections is small and reclaimed; nothing scales with document size, because the page is never held
whole.
