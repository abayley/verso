# RFC-0040 phase 1: request and response path baseline (2026-09-11)

Baseline measurements for RFC-0040, taken before any change, on the real corpus at the current default heap.
The headline is that two of the surveyed paths are worse than the survey's cost model predicted, and one of
them is not a memory multiplier at all but a functional limit that users can reach today.

## Baseline measurement setup

| Item       | Value                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------ |
| Binary     | `build/verso` (MicroHs), commit `7e610bf`                                                  |
| Heap       | `+RTS -H8000000 -RTS` (the current `VERSO_HEAP_CELLS` default, ~122MB arena)               |
| Config     | `build/cello-profile.conf`: real corpus, 3,980 documents, search off, port 8081            |
| Versioning | On, so saves stage a draft under `build/cello-profile/drafts` rather than writing the tree |
| Machine    | The developer's own desktop (Darwin arm64), otherwise idle                                 |
| RSS        | `ps -o rss=`, polled every 100ms for the duration of each request                          |

Startup on this corpus took 16.3s (cold link-index build) and settled at 140MB RSS, which is the 122MB arena
plus the runtime. That is the number every delta below is measured against.

## Document render baseline

The largest document in the real corpus is 263,076 bytes
(`cello-smartsecure/zscaler-management/zscaler-customer-info/zscaler-customer-summary-mitre10.md`).

| Request                 | Duration | Response bytes | RSS delta |
| ----------------------- | -------- | -------------- | --------- |
| `GET` read view         | 141ms    | 356,481        | ~6MB      |
| `GET ?edit` editor view | 100ms    | 356,662        | ~6MB      |

The render path is the healthiest of the three. It holds several copies of the document (read, escape, page,
concat) but at 263KB that is a few megabytes against a 122MB arena, and the wall time is dominated by useful
work. Item 3 in the RFC's inventory is real but is the lowest priority of the three request-path items, which
is a change from the survey's ordering.

## Form save baseline

`POST /documents/<path>` with an `application/x-www-form-urlencoded` body of `markdown=<content>`, content
being ASCII text with `%0A` newline escapes. Body size is the raw request body, which is what `formBodyLimit`
caps at 1 MiB. Each request went to a fresh scratch path.

| Body size | Duration         | Notes                                                                                                           |
| --------- | ---------------- | --------------------------------------------------------------------------------------------------------------- |
| 16KB      | 0.24s            | includes first-request warmup                                                                                   |
| 32KB      | 0.02s            | the reliable small-body figure                                                                                  |
| 64KB      | 30.08s           | 2x the body, ~1,200x the time                                                                                   |
| 128KB     | 160.72s          | 2x the body, 5.3x the time                                                                                      |
| 1,007KB   | did not complete | client gave up at 300s; the server was still at 100% CPU on the request afterwards, and never logged a response |

This is the finding that matters most. The save path is not merely a ~24x memory multiplier as the survey
estimated; between 32KB and 64KB it falls off a cliff and then grows faster than quadratically. RSS stayed
flat at ~137MB throughout, so this is spent CPU, not growth.

Two consequences:

- **The 1 MiB `formBodyLimit` is unreachable.** No client can save a body near the cap. The cap is
  documentation of an intent the code cannot deliver.
- **Documents in the real corpus are already too big to save.** The corpus holds documents of 263KB, 190KB
  and 150KB. Extrapolating the curve, saving any of them takes many minutes. Editing a large existing
  document is effectively broken today, not merely expensive. This reframes RFC-0040 phase 2 from an
  optimisation into a bug fix, and it is the reason phase 2 should stay first in the order.

The cliff shape (flat, then sudden, then super-quadratic) does not look like the per-character cost of the
`String` passes, which would be linear with a large constant. Every pass in the chain is linear and lazy
(`BS.unpack`, `splitOn`, `break`, `Http.decode`, `normaliseNewlines`), and MicroHs's `BS.pack` grows its
buffer geometrically (`bsappbyte` in `eval.c` multiplies capacity by 1.5), so it is amortised linear too.
The likely cause is the fixed arena: once the `String` working set approaches the 8,000,000 cells, every
allocation triggers a mark-and-sweep over the whole arena, so time grows with the square of the live set.
If that is right, RFC-0039's tight heap converted this space bug into a time bug, which is why it has been
invisible: the server never crashes, it just stops finishing.

### Heap-control experiment for the save cliff

The hypothesis was tested the same day by re-running the ladder at `-H32000000` (a 488MB arena, four times
the default), one request at a time. It is confirmed, and the confirmation is more useful than expected.

| Body size | At 8,000,000 cells | At 32,000,000 cells                                    | Speedup |
| --------- | ------------------ | ------------------------------------------------------ | ------- |
| 64KB      | 30.08s             | 0.044s                                                 | ~685x   |
| 128KB     | 160.72s            | 0.085s                                                 | ~1,900x |
| 256KB     | not taken          | did not finish; still at 99% CPU after 150s, abandoned | --      |

Two things follow. First, **the save path is linear when the arena has headroom**: 2x the body costs 1.93x
the time (0.044s to 0.085s). Nothing in the chain is algorithmically quadratic, exactly as reading the code
suggested. The 8,000,000-cell figures were measuring garbage collection, not work.

Second, and this is the important half, **raising the heap does not fix the problem, it only moves the
cliff.** At 8M cells the cliff sits between 32KB and 64KB; at 32M cells it sits between 128KB and 256KB.
Four times the arena buys four times the body size, which is what a live set proportional to the body
predicts. Reaching the 263KB corpus document would take roughly 64M cells (~1GB), and the 1 MiB
`formBodyLimit` roughly 256M cells (~4GB), for one concurrent save.

So the fix is not heap sizing, it is removing the live set: the `String` round-trip costs on the order of a
hundred cells per body byte across the five simultaneous passes (`BS.unpack`, `splitOn`, `break`,
`Http.decode`, `normaliseNewlines`, then `BS.pack`), and the arena needs free space to collect in on top of
that. Phase 2's byte-level decoding removes essentially all of it, which should make the existing
8,000,000-cell default comfortable rather than requiring a bigger one. That keeps RFC-0039's tight,
fail-fast heap intact, and it is the reason this RFC's Non-Goals still rule out raising
`VERSO_HEAP_CELLS`.

The experiment also explains why the tight heap never reported `heap exhausted` on this path. The collector
always finds something to reclaim, because the passes are lazy and the intermediate cells die as they are
consumed; it simply has to run almost continuously to do it. The failure mode of a nearly-full arena here is
unbounded time, not a crash.

## Asset upload baseline

`POST /documents/<path>?asset` with a raw body at the 10 MiB cap (`treeAssetMaxBytes`), filename supplied in
`X-Attachment-Filename`.

| Measure      | Value                             |
| ------------ | --------------------------------- |
| Duration     | 5.57s                             |
| RSS baseline | ~137MB                            |
| RSS peak     | 698MB                             |
| Spike        | ~560MB for a 10MB body, about 56x |
| Stored bytes | 10,485,760, exactly as sent       |

The survey described this as "two copies of a ten-megabyte body". It is about fifty-six. The spike is
consistent with `readBodyStrict`'s `BS.concat` over roughly 2,560 socket chunks being `foldr append`: each
step allocates a new buffer holding everything so far, and all of them are live until the fold finishes.
Note also that this memory is `malloc`'d ByteString payload, outside the cell arena, so the upload path
inflates RSS without ever reporting `heap exhausted`. That is why the tight heap did not catch it either.

## Concurrency measurement not taken

The planned concurrency measurement was four simultaneous 10 MiB uploads. It was run once and it exhausted
the machine's RAM. The server process was observed above **25GB** of resident memory before the desktop
session restarted. Two of the four requests had reported 24.1s and 111.6s before the machine went down.

That 25GB is the most alarming number in this baseline, and it is not a linear extrapolation of the
single-request spike: four requests at the measured ~560MB each would be ~2.2GB, so the per-request cost
under concurrency is roughly 6GB, an order of magnitude worse. The likely reason is that a ByteString's
payload is `malloc`'d rather than allocated in the cell arena, so it does not count toward the pressure that
triggers a MicroHs collection. On a single request the arena filled from the `String` and list allocation
alongside the fold, a collection ran, and the finalizers freed the intermediate buffers as it went. With
four concurrent folds, the intermediates -- roughly 2,560 buffers per request, averaging half the body --
are garbage almost immediately but nothing prompts the collector to notice, so they accumulate until the OS
refuses.

If that is right it is a defect worth stating plainly: **the upload path's memory is invisible to the
collector's trigger heuristic, so under concurrency it grows without bound rather than being reclaimed.**
That is a denial-of-service lever, not a performance wrinkle, and it raises the priority of phase 3's
streaming sink relative to what the single-request figure suggested. It also means neither of RFC-0039's
safety nets applies: not the tight arena, which this memory bypasses, and not `heap exhausted`, which never
fires.

These numbers are an observation from an aborted run, not a repeatable measurement, and the run should not
be repeated as designed.

This was a mistake in test design, not a discovered limit, and it should not be repeated on a workstation.
When the concurrency figure is needed it should be taken with a hard bound: two concurrent requests rather
than four, a smaller body (1 MiB, scaled up arithmetically), an `ulimit -v` or a container memory cap on the
server process, and RSS sampled by the harness with an abort threshold. Better still, take it after phase 3
lands, when the expected answer is a bounded buffer per request and the test is no longer dangerous.

The security point in the RFC no longer rests on the single-request figure alone. A ~560MB transient per
at-the-cap upload would already let a handful of simultaneous uploads exhaust a modest host; the observed
25GB says four are enough to exhaust a developer workstation. What the bounded re-run is for is a defensible
per-request number and confirmation of the trigger-heuristic explanation, not to establish that the problem
exists.

## Corrections to the RFC-0040 inventory

Phase 1 exists to correct the survey where measurement disagrees with it. Three corrections:

| Inventory item                    | Survey said                          | Measurement says                                                        |
| --------------------------------- | ------------------------------------ | ----------------------------------------------------------------------- |
| `treeSave` `String` round-trip    | ~24x memory multiplier               | a functional limit: unusable past ~64KB, and corpus documents exceed it |
| `treeUpload` and `storeAsset`     | two copies of the body               | ~56x the body in transient RSS, outside the cell arena                  |
| Document render whole-page concat | 4-5 copies per response, ranked high | real but cheap at corpus sizes; lowest priority of the three            |

The phase ordering in the RFC (form decoding, then upload streaming, then response streaming) is confirmed
by these numbers, and phase 2's justification is stronger than the RFC currently states.
